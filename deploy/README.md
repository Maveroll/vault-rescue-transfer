# Развёртывание ретранслятора

Версия 0.3.0: сборка `npm run build` создаёт `dist/relay.cjs` и `dist/receiver.cjs`. Обе утилиты работают с Node.js 22+ без установки дополнительных зависимостей на целевой машине.

## Установка

1. Скопировать `relay.cjs` в `~/vault-rescue-transfer/` серверного пользователя.
2. Создать вне Git файл `relay.env` по примеру `relay.env.example`. `RELAY_KEY` — случайный секрет из 32 байт в hex, права файла `0600`. Этот ключ нужен только приёмнику для создания сеансов.
3. Выбрать `HOST`, доступный обратному прокси, и свободный `PORT`. При прокси в контейнере `127.0.0.1` контейнера не является адресом хоста; выбрать внутренний адрес хоста в сети прокси. Не публиковать backend напрямую в Интернет.
4. Установить `vault-rescue-relay.service` в `~/.config/systemd/user/`, затем выполнить `systemctl --user daemon-reload` и `systemctl --user enable --now vault-rescue-relay.service`. Для работы после выхода пользователя нужен включённый linger.
5. Добавить отдельный HTTPS-маршрут по `traefik.example.yml`, предварительно сохранив резервную копию действующей конфигурации. Не заменять существующие маршруты примером целиком. Пример предполагает `websecure` и resolver `letsencrypt`; адаптировать к серверу.
6. Проверить `GET /vault-rescue/health`: ожидается JSON с `status: ok` и `protocol: 1`. Проверить, что прежние маршруты продолжают работать.
7. На компьютере хранить копию административного ключа в отдельном приватном файле вне Git; путь передать приёмнику через `--key-file`. Сам ключ не помещать в аргументы команды или журнал.

Приёмник запускается на один снимок и показывает временный код для плагина. Сервер выдаёт отдельные случайные ключи отправителю и приёмнику. Приёмник завершает ожидание после 15 минут без данных. Один запрос передачи ожидает подтверждения до 150 секунд; слишком медленные операции завершатся ошибкой, а не ложным успехом.

## Минимальные условия

- Доступный отправителю и компьютеру адрес с корректным HTTPS-сертификатом.
- Поддержка обычных HTTP-запросов и long polling до 20 секунд. Для запросов отправки нужен таймаут прокси не менее 180 секунд.
- Ограниченные буферы и передача с учётом скорости приёмника.
- Отсутствие записи содержимого хранилищ на диск, в кэш, дампы запросов и журналы. Настройки обратного прокси также должны удовлетворять этому условию.
- Временные коды сессий, ограничение попыток подключения и очистка состояния после завершения или истечения срока сессии.
- Журналы только технических событий без содержимого файлов, имён заметок и кодов подключения.

Ретранслятор не ставит хранилища в очередь на диске. Не более восьми сеансов, в каждом не более одного неподтверждённого сообщения до 300 КБ. Приложение не пишет тела запросов и коды в журнал. Дампы процессов отключены в unit-файле. TLS не скрывает содержимое от оператора ретранслятора: сквозного шифрования пока нет.

После обрыва незавершённая копия остаётся на компьютере, следующий запуск создаёт новую папку. Версия 0.3.1 проверяет и использует готовые файлы прежних снимков локально, без повторной передачи. Обновите все три компонента. Повтор poll возвращает неподтверждённое сообщение, повтор ack с последним ID безопасен; это позволяет приёмнику повторить временно неудавшийся запрос.

## Проверка перед основной передачей

Проверить соединение, передачу крупнейшего тестового файла, обрыв и повторное подключение. Убедиться, что память сервера не растёт пропорционально объёму переданного хранилища и что содержимое не появляется во временных файлах или журналах.

Адреса конкретного сервера и секреты хранятся вне репозитория. Установка ретранслятора не должна менять действующую базу синхронизации или задания резервного копирования.
